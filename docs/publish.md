# Publish

Desired user-facing behavior for [SOX-138](https://linear.app/soxtoby/issue/SOX-138/implement-focused-active-stack-publication-and-publish-receipts), from the stack sync, publication, and conflict policy settled in SOX-116 (2026-08-18).

## Accepted decisions

- Publish is a separate explicit action for a branch's Active Stack, up to and including that branch. It updates changed intermediate and tip branches, never its Base Branch, unrelated branches, or other open stacks. In the desktop it is offered on each branch header with something to publish (settled 2026-10-24); the receipt's Resume and restoration stay in the command line.
- A changed branch without an upstream creates a same-named branch on the selected remote and records that upstream. The control shows every destination before activation.
- A lease-valid non-fast-forward update runs automatically, without a second force confirmation. The control visibly changes to indicate Force publish and identifies every affected ref.
- The Primary Branch has no Base, so it publishes alone, from its own header. Because everyone's work builds on it, the desktop asks before publishing it, and warns when that would force (settled 2026-10-26).
- Any stale lease aborts publication and offers Pull latest. Laneway never silently refetches, rewrites, or retries.
- Prefer an atomic multi-ref push. If the remote lacks atomic push, preflight every remote tip, then publish sequentially from the lowest changed stack branch toward the tip. Stop at the first failure, keep successful updates, and persist a Publish Receipt that exposes Resume.
- Rollback is never automatic. Restoring earlier remote tips is a new explicit, lease-guarded Force publish.
- Publish is not part of ordinary undo/redo. Local operations remain independently undoable.
- An Unresolved Stack, or a stack depending on one, cannot publish until every deferred conflict is resolved.
- V1 depends only on ordinary Git remote behavior. Provider protections and PR-branch ownership arrive with the Provider Overlay; until then the remote server's answer is the only authority.

## Implementation

`lane publish --request <JSON> --json` is the Engine entry point. A `plan` request names a branch and returns its Active Stack, every update, a token, any reason publication is blocked, and the newest receipt touching the stack. A `plans` request names several branches and returns each one's plan, as `plan` would, without the receipt, or the reason it can't be planned; they share one reading of the repository (its remotes, Branch Graph, and local branches, and each branch's update), which is most of a plan's cost. A `publish` request carries the reviewed token; if planning now gives a different result the Engine refuses, so what was shown is what is pushed. `resume` and `restore` name a receipt. Progress events name the remote check and each push. Both `--request` and the ordinary command line exit with status 1 when anything is left unpublished (blocked, partial, stale, or failed). `lane publish --preview` previews a stack's publish only; combining it with `--resume` or `--restore` is a usage error.

The Active Stack is derived exactly as Pull latest derives it (`cli/src/active-stack.ts`). Its first member is the Base Branch and is never published, so a stack consisting only of its Base has nothing to publish. The Primary Branch is the exception: it has no Base, so its stack is itself alone, and it publishes by itself. Only its same-named local branch is the Primary Branch (`primaryLocalRef` in `shared/src/branch-graph.ts`), since that alone publishes to it; another local branch sharing its tip shares its Branch Node but plans as that node's Base. Every other local branch whose tip differs from its destination's remote-tracking tip is an update: `create` when the remote branch is absent, `update` for a fast-forward, `force` otherwise. A branch strictly behind its remote is left alone, since publishing it would rewind the remote. Destinations are always same-named branches: on the upstream's remote when the branch has one, otherwise on the selected remote (the request's, then the repository setting, then the only remote). A branch without a same-named upstream records `<remote>/<branch>` as its upstream once published, as `git push -u` does. The existing conflict `publish-check` guard blocks Unresolved Stacks, and Resume applies it to the receipt's branches before pushing the receipt's own commits.

Every update carries an exact lease, `--force-with-lease=<ref>:<oid>`, from the remote-tracking ref read at planning; a create leases on absence. Laneway does not pass `--force-if-includes`: with an explicit `<expect>` value it is a no-op, so the exact lease is the whole remote check. A Laneway fetch records the upstream tip each branch last pulled ([Pull latest](pull-latest.md)), so a stack is blocked with "<remote>/<branch> changed since the last pull. Pull latest, then publish again." while a branch publishing to its own upstream lacks commits a Laneway fetch brought since; a lease never comes from commits Laneway fetched but no pull integrated. The visible Force publish label is the protection against overwriting commits another tool fetched but nobody integrated.

Publish, Resume, and restoration share one path. The receipt is written first, then `git ls-remote` reads every destination the receipt names, including ones it already recorded as published. It reads the remote's push URL (`git remote get-url --push`), not its fetch URL, because that is the repository the push changes; a remote with several push URLs is refused until receipts record each one. An update whose remote already holds its target is marked published without pushing; this is how a receipt verifies its postconditions after a crash or restart. A published update whose remote has since moved is stale, and so is any other mismatch with the lease; either aborts the attempt before anything is pushed. A remote that cannot be read aborts it too: the receipt is verified whole, so every update not yet published, on every remote, fails with Git's diagnostic, and recorded successes stay published. Otherwise the Engine runs `git push --atomic --porcelain --no-follow-tags --recurse-submodules=no` with every lease, so `push.followTags` and submodule recursion cannot push refs the receipt does not name (explicit refspecs already bypass `push.default` and `remote.<name>.push`). When Git reports that the remote does not support atomic push, which it does before sending anything, the Engine pushes one branch at a time from the bottom of the stack, saving the receipt after each, and stops at the first refusal. Cancellation is checked once the receipt is saved, immediately before the first push, and between sequential pushes. Pushes spanning more than one remote are always sequential. Git hooks and credential helpers run as usual; a failing `pre-push` hook or a refused credential fails the attempt without pushing.

After the remote answers, the receipt is saved, then every published update's remote-tracking ref is moved from the receipt's lease to its target if nothing has moved it since (Git does this itself for a normal push, but not when a crash lost the push's outcome), and upstreams are recorded. A configuration error there is reported alongside the saved receipt rather than hiding what was published.

Each receipt update is `pending`, `published`, `stale`, or `failed`, with Git's diagnostic for refusals, including a remote hook's own output. The receipt's status follows: published when everything is, stale when any lease was stale (the next action is Pull latest), partial when anything published, failed otherwise. Successes are never rolled back. Resume pushes what remains with the receipt's own leases. Restoration first reads the remote for every update the receipt did not record as published, so an update that reached the remote before a crash is restored too. If a remote cannot be read, restoration restores nothing and fails with Git's diagnostics, since an unrecorded push may have reached it. It then creates a new `restore` receipt that pushes each published update's earlier tip back, leasing on the tip it published, and deletes branches the original publish created; their upstream configuration stays, so the next Publish recreates them.

Receipts live at `<git-common-dir>/laneway/publish/<id>.json`, one per publish, rewritten durably (temporary file, flush, rename) before any push and after every outcome. Identifiers are word characters and hyphens and sort by creation time; a receipt whose recorded `id` is not its file name is ignored, so it can never be written elsewhere. The newest 100 finished receipts are kept, and a publish never prunes its own receipt or the one it restores, so an old receipt being resumed stays on disk while it pushes. A receipt Resume may still need is never pruned: one with some updates published and others not, or one whose attempt stopped before Git answered (only pending and published updates). A damaged receipt is ignored: it loses Resume and restoration, never branches.

Every receipt retains the commits it names, both the leased remote tips and the targets, in Operation History's protected packs ([ADR 0014](adr/0014-retain-operation-objects-in-protected-packs.md)) under the key `publish-<id>`, so Resume and restoration survive reflog expiry and pruning. Pruning a receipt releases them. Retention briefly takes the repository mutation lock, which covers every change to retained objects.

Publish runs outside the recovery journal and Operation History, holding the mutation lock only to retain its receipt's commits; it changes only remote refs, remote-tracking refs, and upstream configuration. An operation's record holds only the branch configuration it changed, so a later Publish never makes it look externally changed, and undo keeps a surviving branch's current upstream unless the operation itself changed it; native undo validation ignores `branch.<name>.remote` and `branch.<name>.merge` for the same reason and restores exactly the upstream configuration its Git command changed.

Known limits: a remote with nonstandard fetch refspecs has no remote-tracking ref for a same-named destination, so its branches always plan as creates and the lease refuses them.

The renderer offers **Publish** as an icon on each branch header in the Commit Trails whose branch has something to publish: a local branch above its trail's Base, or the Primary Branch, whose own remote branch lacks its tip, which the header's colour already shows (`offersPublish` in `publish.ts`). It publishes that branch's Active Stack, so a header lower in a stack publishes less. One `plans` request plans every offered branch across the open columns whenever the Branch Graph or those branches change, so each icon has its plan before it is pressed; a branch keeps its last plan while it is planned again. Until its plan arrives the icon is disabled, and a plan with nothing to publish hides it. The icon's tooltip names it, as **Publish** or **Force publish** and the branches it updates, and lists every destination (`origin/<branch>`) with its kind, marking new branches and those that will record an upstream. The icon shows the stack's most consequential update: when any update is non-fast-forward its arrow doubles and turns red and the force-with-lease refs are marked; otherwise, when the stack creates a remote branch, its bar is dashed. That visible state is the only confirmation, except for the Primary Branch: its icon opens a dialog naming its destination, with Cancel focused when it would force and a warning that the remote's commits the branch lacks will go from the remote; Cancel and Escape publish nothing (`PublishConfirmation` in `publish-control.tsx`). The dialog keeps the plan it opened with, so planning again meanwhile can't turn it into a Force publish under a focused button; going ahead publishes that plan's token, which the Engine refuses if the stack changed since. Its header publishes the Primary Branch's own local branch, never another sharing its tip (`publishRef`). A stack that can't publish, such as an Unresolved Stack, keeps its icon disabled with the plan's reason as its hint. While the Engine runs, the icon shows progress beside it and the repository's other icons wait; success is a passing notice with no Undo, since Publish is outside Operation History, and it never replaces a notice offering Undo for a local operation, showing once that notice closes instead. Once the branch is published its icon goes, and focus falls back to the column. A partial, failed, or stale result opens an outcome, shown while its repository is active, listing each update's result with Git's diagnostic, what stayed as it was, and the way forward: **Pull latest** after a stale lease (never a retry), otherwise publishing again from the header, which plans whatever is left. Closing a repository forgets its publishes, so a result arriving afterwards is dropped. The desktop offers neither Resume nor restoration; `lane publish --resume` and `--restore` still use the receipts.
