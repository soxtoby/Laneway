# Publish

Desired user-facing behavior for [SOX-138](https://linear.app/soxtoby/issue/SOX-138/implement-focused-active-stack-publication-and-publish-receipts), from the stack sync, publication, and conflict policy settled in SOX-116 (2026-08-18).

## Accepted decisions

- Publish is a separate explicit action for the focused Active Stack. It updates changed intermediate and tip branches, never its Base Branch, unrelated branches, or other open stacks.
- A changed branch without an upstream creates a same-named branch on the selected remote and records that upstream. The control shows every destination before activation.
- A lease-valid non-fast-forward update runs automatically, without a second force confirmation. The control visibly changes to indicate Force publish and identifies every affected ref.
- Any stale lease aborts publication and offers Pull latest. Laneway never silently refetches, rewrites, or retries.
- Prefer an atomic multi-ref push. If the remote lacks atomic push, preflight every remote tip, then publish sequentially from the lowest changed stack branch toward the tip. Stop at the first failure, keep successful updates, and persist a Publish Receipt that exposes Resume.
- Rollback is never automatic. Restoring earlier remote tips is a new explicit, lease-guarded Force publish.
- Publish is not part of ordinary undo/redo. Local operations remain independently undoable.
- An Unresolved Stack, or a stack depending on one, cannot publish until every deferred conflict is resolved.
- V1 depends only on ordinary Git remote behavior. Provider protections and PR-branch ownership arrive with the Provider Overlay; until then the remote server's answer is the only authority.

## Implementation

`lane publish --request <JSON> --json` is the Engine entry point. A `plan` request names the focused column's branch and returns its Active Stack, every update, a token, any reason publication is blocked, and the newest receipt touching the stack. A `publish` request carries the reviewed token; if planning now gives a different result the Engine refuses, so what was shown is what is pushed. `resume` and `restore` name a receipt. Progress events name the remote check and each push. Both `--request` and the ordinary command line exit with status 1 when anything is left unpublished (blocked, partial, stale, or failed). `lane publish --preview` previews a stack's publish only; combining it with `--resume` or `--restore` is a usage error.

The Active Stack is derived exactly as Pull latest derives it (`cli/src/active-stack.ts`). Its first member is the Base Branch and is never published, so a stack consisting only of its Base has nothing to publish. Every other local branch whose tip differs from its destination's remote-tracking tip is an update: `create` when the remote branch is absent, `update` for a fast-forward, `force` otherwise. A branch strictly behind its remote is left alone, since publishing it would rewind the remote. Destinations are always same-named branches: on the upstream's remote when the branch has one, otherwise on the selected remote (the request's, then the repository setting, then the only remote). A branch without a same-named upstream records `<remote>/<branch>` as its upstream once published, as `git push -u` does. The existing conflict `publish-check` guard blocks Unresolved Stacks, and Resume applies it to the receipt's branches before pushing the receipt's own commits.

Every update carries an exact lease, `--force-with-lease=<ref>:<oid>`, from the remote-tracking ref read at planning; a create leases on absence. Laneway does not pass `--force-if-includes`: with an explicit `<expect>` value it is a no-op, so the exact lease is the whole remote check. Because Laneway itself only fetches during Pull latest, which integrates what it fetches, the visible Force publish label is the protection against overwriting commits another tool fetched but nobody integrated.

Publish, Resume, and restoration share one path. The receipt is written first, then `git ls-remote` reads every destination the receipt names, including ones it already recorded as published. It reads the remote's push URL (`git remote get-url --push`), not its fetch URL, because that is the repository the push changes; a remote with several push URLs is refused until receipts record each one. An update whose remote already holds its target is marked published without pushing; this is how a receipt verifies its postconditions after a crash or restart. A published update whose remote has since moved is stale, and so is any other mismatch with the lease; either aborts the attempt before anything is pushed. Otherwise the Engine runs `git push --atomic --porcelain --no-follow-tags --recurse-submodules=no` with every lease, so `push.followTags` and submodule recursion cannot push refs the receipt does not name (explicit refspecs already bypass `push.default` and `remote.<name>.push`). When Git reports that the remote does not support atomic push, which it does before sending anything, the Engine pushes one branch at a time from the bottom of the stack, saving the receipt after each, and stops at the first refusal. Cancellation is checked once the receipt is saved, immediately before the first push, and between sequential pushes. Pushes spanning more than one remote are always sequential. Git hooks and credential helpers run as usual; a failing `pre-push` hook or a refused credential fails the attempt without pushing.

After the remote answers, the receipt is saved, then every published update's remote-tracking ref is moved from the receipt's lease to its target if nothing has moved it since (Git does this itself for a normal push, but not when a crash lost the push's outcome), and upstreams are recorded. A configuration error there is reported alongside the saved receipt rather than hiding what was published.

Each receipt update is `pending`, `published`, `stale`, or `failed`, with Git's diagnostic for refusals, including a remote hook's own output. The receipt's status follows: published when everything is, stale when any lease was stale (the next action is Pull latest), partial when anything published, failed otherwise. Successes are never rolled back. Resume pushes what remains with the receipt's own leases. Restoration first reads the remote for every update the receipt did not record as published, so an update that reached the remote before a crash is restored too. It then creates a new `restore` receipt that pushes each published update's earlier tip back, leasing on the tip it published, and deletes branches the original publish created; their upstream configuration stays, so the next Publish recreates them.

Receipts live at `<git-common-dir>/laneway/publish/<id>.json`, one per publish, rewritten durably (temporary file, flush, rename) before any push and after every outcome. Identifiers are word characters and hyphens and sort by creation time; a receipt whose recorded `id` is not its file name is ignored, so it can never be written elsewhere. The newest 100 finished receipts are kept. A receipt Resume may still need is never pruned: one with some updates published and others not, or one whose attempt stopped before Git answered (only pending and published updates). A damaged receipt is ignored: it loses Resume and restoration, never branches.

Every receipt retains the commits it names, both the leased remote tips and the targets, in Operation History's protected packs ([ADR 0014](adr/0014-retain-operation-objects-in-protected-packs.md)) under the key `publish-<id>`, so Resume and restoration survive reflog expiry and pruning. Pruning a receipt releases them. Retention briefly takes the repository mutation lock, which covers every change to retained objects.

Publish runs outside the recovery journal and Operation History, holding the mutation lock only to retain its receipt's commits; it changes only remote refs, remote-tracking refs, and upstream configuration. So that recording an upstream never makes a Laneway Operation look externally changed, checkpoint identity and native undo validation ignore `branch.<name>.remote` and `branch.<name>.merge`. Undo and redo of a checkpointed operation keep a surviving branch's current upstream unless the operation itself changed it; native undo restores exactly the upstream configuration its Git command changed.

Known limits: a remote with nonstandard fetch refspecs has no remote-tracking ref for a same-named destination, so its branches always plan as creates and the lease refuses them.

The renderer places **Publish** at the foot of the focused Workspace Column when it shows a local branch, so it publishes that column's stack and moves with focus; sitting at the foot, it never shifts the rows above it. It lists the stack and every destination (`origin/<branch>`) with its kind, marking new branches and those that will record an upstream, and becomes a red **Force publish** labelling each force-with-lease ref when any update is non-fast-forward. That visible state is the only confirmation. With nothing to publish, or a reason it can't, it is disabled and its hint gives the plan's reason. The control plans again whenever the Branch Graph changes. While the Engine runs it shows the Engine's progress; success is a passing notice with no Undo, since Publish is outside Operation History, and it never replaces a notice offering Undo for a local operation, showing once that notice closes instead. A partial, failed, or stale result opens an outcome, shown while its repository is active, listing each update's result with Git's diagnostic, what stayed as it was, and the way forward: **Pull latest** after a stale lease (never a retry), otherwise **Resume**. A Resume refused for an Unresolved Stack shows only its reason. Closing a repository forgets its publishes, so a result arriving afterwards is dropped. The stack's latest receipt, read with every plan and so surviving a restart, offers **Resume** while it is incomplete and restoration when a publish put anything on the remote. Each lists the receipt's own destinations before it is pressed: Resume what the receipt left unpublished, and restoration each published ref forced back with lease to its earlier tip, or deleted if the publish created it, under a red **Force publish earlier tips** button.
