# Pull latest

Desired user-facing behavior for [SOX-137](https://linear.app/soxtoby/issue/SOX-137/implement-pull-latest-for-open-active-stacks). Shared understanding confirmed on 2026-09-20; implementation landed the same day.

## Accepted decisions

- Pull latest incorporates incoming changes from each stack branch's upstream, then synchronizes the stack onto its updated Base. Fetched tips remain frozen for the operation.
- A branch that is published, or has a published branch built on it, stays where it is when the Primary Branch under it only moved forward. Restacking it would rewrite published history, leaving a Force publish pending after every pull. It still takes its own upstream's commits, replaying local-only commits onto them when both moved. A branch is published while its upstream exists, whether or not its column is open. Restack, on the Base's heading in the branch's column, moves it when the user chooses; it runs at once with Undo, and fetches and publishes nothing. Only the lowest branch of a stack stays, and only against the Primary Branch: Base inference keeps the Primary Branch as a branch's Base however far it moves on, while any other two branches that each move past their fork both fall back to the Base below them. So the branches above the lowest follow the one below them, and a stack on any other Base restacks, as before (settled 2026-11-11).
- An open Active Stack includes its intermediate branches even when they have no Workspace Column. Branches outside all open stacks remain untouched. Local Base Branches retain the existing fast-forward-only rule; diverged Bases are never reset or rewritten automatically.
- Working Changes are automatically preserved and reapplied in their original worktrees. Reapplication conflicts use deferred recovery; independent stacks continue. The existing Working Changes Conflict contract applies: accepted resolutions become Working Changes, not commits.
- When a feature branch and its upstream both advance, replay local-only commits onto incoming history, preserving merge topology and deferring conflicts normally.
- Adopt a force-pushed upstream automatically only when unpublished local work can be reliably distinguished from replaced history. Otherwise leave the affected stack unchanged and explain the explicit decision required.
- A diverged Base blocks synchronization of stacks based on it. Show "Base has diverged" and continue independent stacks; never silently bypass the local Base.
- Pull latest may update an already Unresolved Stack onto newer fetched history. Preserve resolutions whose inputs remain unchanged; reopen affected conflicts and retain previous resolutions as suggestions.
- Fetch the selected remote and every other remote needed by the open Active Stacks, once each.
- Activating Pull latest starts immediately, with progress and per-stack outcomes. Decisions that cannot be made automatically leave the affected stack unchanged with an explanation.
- Freeze scope at activation, including collapsed Workspace Columns. Opening or closing columns during execution affects the next pull, not the current operation.
- Pull latest is started from a Workspace Column and updates that column's Active Stack. Every open stack sharing a branch above its Base with it joins the pull, so no open branch is left on history the pull replaced; open stacks sharing only the Base stay as they are, since a Base only moves forward. Branches outside every open stack are left to background fetching (settled 2026-10-28, replacing the repository-wide pull).
- Cancellation stops at the next safe boundary, retaining completed updates and preserved edits. Report what completed and what remains.
- One Undo reverses the pull's completed local changes across stacks, including restored Working Changes, when replay preconditions remain valid. Fetch results remain available.
- If a required fetch fails, skip stacks that depend on it with an actionable error; continue stacks whose required fetches succeeded. Never substitute stale fetched history.
- A branch without an upstream still synchronizes onto its Base. A configured upstream that has disappeared is treated the same way: there is nothing to incorporate, nothing to report, and Laneway never silently recreates its remote branch.
- Recheck inputs before applying changes. If concurrent file edits or ref movements invalidate preparation, leave the affected stack untouched by this pull and report "Changed during pull—retry"; independent stacks continue.
- Skip the overlapping stack group containing an active Historical Edit, preserving that session; independent stacks continue.
- Existing Working Changes Conflicts do not prevent an update. Preserve edits and conflict tracking, retain progress where inputs match, and reopen changed conflicts with earlier resolutions available as suggestions.
- Place Pull latest on the heading of each column's own branch, beside Publish. It takes the accent colour while the Branch Graph knows of commits waiting for the stack, listing them in its tooltip. While it runs it becomes Cancel, with fetching/updating progress beside it; only one pull runs in a repository at a time. The repository header has Fetch in its place, which fetches at once and says when the last fetch finished or why it failed (settled 2026-10-28).
- When every stack updated cleanly or was already current, confirm with a passing notice only. Otherwise show a compact repository outcome summary, expandable by stack: Updated, Already current, Needs resolution, Skipped, or Failed. Explain skips and failures, link conflicts to inline resolution, and keep publication pending visible on affected branches.
- After interruption, safely recover interrupted local changes without automatically continuing the pull. Retain completed updates, conflict progress, and the pull's single Undo entry; explain anything recovery cannot safely finish. Continuing requires another explicit Pull latest.
- With no remotes, disable Pull latest and show "Add a remote to pull." A pull with no stacks in scope only fetches and reports "Fetched; no open stacks to update." A pull with no local changes creates no Undo entry.
- When an upstream rewrite cannot be adopted safely, offer inspection of local and upstream history and explain that Laneway cannot identify which local commits to retain. The user reconciles through explicit history operations, then retries; never automatically reset or guess which commits to replay.
- Laneway fetches the active repository in the background, without prompting for credentials, and fast-forwards local branches strictly behind their upstreams, except branches checked out in a worktree, branches in the Active Stack of an open column or a checked-out branch, and branches in an Unresolved Stack or Historical Edit; those wait for Pull latest. Background fetching stays outside Operation History (settled 2026-10-28).

## Existing policy

- Pull latest never publishes. Rewritten publication remains pending.
- Overlapping stacks synchronize as one unit; independent stacks may complete separately.
- Unknown or ambiguous Bases block automatic synchronization of the affected stack while leaving inspection available.
- Commit conflicts produce durable Unresolved Stacks using the [existing recovery contract](unresolved-stack-recovery.md).
- Local mutations remain undoable when their preconditions remain valid.

## Implementation

`lane pull --request <JSON> --json` is the Engine entry point. The request carries the branch of the column it started from, every open Workspace Column's local branch, frozen by the renderer at activation, and the selected remote; `restack`, which `lane pull --restack` sets, restacks published branches too. The Engine reads each of their Active Stacks and keeps the column's stack and, repeatedly, each open stack sharing a branch above its Base with one already kept. `lane pull <branch>...` names its stacks and carries none along. Progress events name each fetch and each stack update; the result lists fetch outcomes and one outcome per stack: `updated`, `current`, `needs-resolution`, `skipped`, `failed`, or `cancelled`, each with an explanation.

Fetching runs before the repository mutation lock so a slow network never blocks other Laneway Operations. Laneway fetches the selected remote and every upstream remote used by scoped stacks once each, with pruning. Fetch results are never part of the undoable operation, so what a branch last pulled has to outlive the fetch (`cli/src/pulled-upstreams.ts`). Another tool's fetch records nothing, so each Laneway fetch also looks for upstreams moved that way: for a branch without a record that lacks its upstream's tip, when the upstream's reflog shows the tip arrived by anything but Laneway's own fetch, the record is the newest tip in that reflog which a tip in the branch's own reflog contains. The same reading forgets a record once the upstream's tip is one the branch held, as after a push by another tool. Without reflogs to read, the tip this fetch moved the upstream from stands in, as before. When a fetch moves a branch's upstream, Laneway records the tip it moved from in `branch.<name>.lanewayPulledUpstream`, unless an earlier fetch already did, and forgets the records of branches that have since caught up. It does so under the mutation lock but outside any operation, ignoring cancellation, whether or not the pull goes on to update anything. Updating a stack compares each upstream with its record, or with its remote-tracking tip when there is none, to tell a force-pushed upstream from ordinary advancement and to recognize local history rewritten since the last pull; it clears an updated branch's record inside the operation, so Undo restores it and a later pull incorporates the same commits again. A branch the pull replayed onto another Base holds copies of its upstream's commits rather than the upstream's tip, so there the record becomes that tip, and stays until the branch's history holds its upstream's tip again; Publish clears it. Native undo and checkpoints ignore these keys, as they do the upstreams Publish records.

Active Stacks are derived from Branch Graph Base inference. When two branches that diverged from each other name one another as Base, the stack continues below the loop through the next closest branch outside the chain; an ambiguous Base skips the stack. Longer chains process first, so overlapping stacks synchronize their shared prefix once and the shorter stack reports the shared result.

Synchronization reuses the SOX-136 stack rewrite. `rewriteStack` accepts explicit replay sources per branch: incoming upstream commits first, then local-only commits, with `git cherry` dropping local commits whose patch is already upstream. A Base fast-forward is a rewrite with no sources, so worktrees holding the Base carry their Working Changes through the same replay and defer reapplication conflicts as Working Changes Conflicts. Existing Unresolved Stacks receive incoming commits as inserted steps and move to the new Base; conflicts whose inputs are unchanged keep their candidates, and changed conflicts keep earlier results as suggestions. Existing Working Changes Conflicts on a moved worktree are re-based onto the new HEAD so acceptance and Keep stashed remain available. A stack is already current only when nothing arrived and each branch already sits on its parent's tip, so a Base that moved before the pull, including a remote-only Base, still restacks it.

A published branch holds what it is built on. Before fetching, the Engine walks the Base chain of every local branch with an upstream, in or out of scope, down to the branch resting on the Primary Branch; after fetching, the upstreams that still exist name the branches that stay. Such a branch at the bottom of a stack, on a Primary Branch the pull only moved forward, is in no rewrite when nothing arrived for it. When its upstream has commits, its rewrite starts from the upstream's tip in place of the Base's: no sources when it is strictly behind or adopts a rewrite, its local-only commits when both moved. The branches above it are planned as ever, onto whatever tip it ends at. An Unresolved Stack is one unit, so one resting on the Primary Branch stays only while nothing arrives for any of its branches. A stack whose branches all stay, on a Base that did not move, is already current.

Background fetching is `lane fetch --request <JSON> --json`, whose request carries the open Workspace Column branch refs and the selected remote (`cli/src/fetch-latest.ts`). It fetches the selected remote and every remote a local branch tracks before taking the mutation lock, then under the lock records the upstreams it moved as Pull latest does and fast-forwards each local branch whose upstream is strictly ahead, unless the branch is left for Pull latest as above. It reads the Branch Graph, for the Active Stacks, only when some branch could move. Each fast-forward is a compare-and-swap `update-ref` with a `laneway: fast-forward` reflog message, and nothing moves while an interrupted operation awaits recovery. The desktop's main process runs it with `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never`, and, unless the user chose an ssh command, ssh in batch mode, so nothing waits for an answer nobody can give. It runs one fetch per repository at a time; Pull latest waits for one under way, and a fetch asked for during a pull reports itself cancelled. The renderer (`background-fetch.ts`) fetches the active repository once its Branch Graph has loaded, so its open columns are known, then every five minutes while the window has focus, and on returning to the window once the last fetch is a minute old. The repository watcher refreshes the Branch Graph when refs move. The header's Fetch fetches at once, however recent the last fetch; its tooltip gives the time the last good fetch finished, and a failed fetch's reason stays in its hint until a fetch succeeds.

Every stack update happens inside one `pull.latest` Laneway Operation, giving one Undo entry across stacks; a pull that changes nothing records no entry. A stack failure before it changes any ref is reported and the pull continues; a failure after refs changed stops the operation under the normal recovery contract. Cancellation is checked between fetches and between stack runs.

Known limits in this release: replay is linear, so stacks whose commits include merges are skipped with an explanation rather than replayed with merge topology; a fetch by another tool is recognized only from reflogs, so where they are disabled or have expired, the upstream's new commits on a branch that has diverged look already pulled and are not incorporated. A stack holding a Historical Edit, and any stack overlapping it, is skipped with an explanation.

The renderer places **Pull latest** on the heading of each column's own local branch, beside Publish (`pull-control.tsx`). The Branch Graph marks each branch whose known Base's tip is outside its history (`behindBase`), and each whose upstream has commits the pull would incorporate (`upstreamIncoming`), reading the pulled-upstream records as the Engine does: a branch that has diverged from an upstream it already pulled was rewritten locally, so the commits it replaced are not incoming and its publication is pending instead. So the button takes the accent colour when a branch in the column's Active Stack is behind its upstream or its Base, and its tooltip lists which; otherwise it says the stack is up to date as of the last fetch. A branch the pull would leave behind the Primary Branch doesn't count (`staysBehind` in `pull-latest.ts`, which reads publication from the whole graph as the Engine does), so the button never asks for a pull that would change nothing. In a column's trail, the heading of a Base that a local branch built on it has fallen behind says how many commits ahead it is (`baseAhead`, which the Branch Graph counts), with **Restack** beside it (`commit-trail.tsx`). Restack is the Branch Graph's rebase onto the Base's own tip with the branches built on it (`restack` in `branch-rebase.ts`): it reviews and runs at once, without the dialog that asks before rewriting published history, since that is what it was pressed for; conflicts and commits it would empty still open the dialog. A clean one confirms with a notice offering Undo. It is disabled with "Add a remote to pull." when the Branch Graph reports no remotes, and with "Another pull is running." in other columns while one runs. While running it becomes **Cancel pull**, with fetch and update progress beside it. An uneventful pull confirms with a passing notice; otherwise an outcome dialog lists fetches and per-stack results, with **Resolve in <branch>** opening the affected column for inline resolution. A stale publish's **Pull latest** pulls the published branch's stack the same way.
